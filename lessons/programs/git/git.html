Git

Yazdığımız kodları güvenle saklamak ve geçmişe dönük değişiklikleri takip edebilmek için Git'i öğreniyoruz. İlk dersten itibaren versiyon kontrolünün mantığını kavrayıp, kayıt döngüsünden dallanma (branching) ve ileri seviye kurtarma işlemlerine kadar tüm temel süreçleri adım adım inceleyeceğiz. Bu süreç sayesinde hatalı yazdığınız kodları kolayca geri alabilecek ve projelerinizin kontrolünü tamamen elinizde tutabileceksiniz. Daha fazla teknik detay ve kaynak için Araçlar sekmesine göz atabilirsiniz.

1. Temeller ve Kayıt Döngüsü

6 Ders

1. Ders: Versiyon Kontrolü ve Git Nedir?

Versiyon Kontrolü ve Git Nedir?

Bir proje, rapor veya analiz dosyası üzerinde çalışırken klasörünün şu hale geldiği mutlaka olmuştur:

# Klasördeki klasik versiyon kaosu: satis_analizi.py satis_analizi_yeni.py satis_analizi_son.py satis_analizi_gercekten_son_v2.py

Bu yöntem bir süre sonra hangi dosyada neyi değiştirdiğini unutmana, çalışan kodu yanlışlıkla bozmana ve saatlerce geriye dönük hata aramana neden olur. Versiyon Kontrol Sistemi (VCS) tam olarak bu kaosu bitirmek için vardır.

Versiyon Kontrolü Ne İşe Yarar?

Versiyon kontrolü, dosyalarının zaman içindeki tüm değişikliklerini kaydeden bir zaman makinesi gibidir.

  • Geçmişi Saklar: Hangi gün, hangi dosyada, tam olarak hangi satırı değiştirdiğini kaydeder.
  • Geri Dönüş Sağlar: Kodunu bozduğunda veya yanlış bir analiz yöntemi denediğinde, tek bir komutla 3 gün önceki çalışan haline dönebilirsin.
  • Güvenli Deneme Alanı Sunar: Ana dosyanı bozmadan farklı fikirler deneyebilir, beğenirsen ana projene dahil edebilirsin.

Git Nedir?

Git, dünyanın en yaygın kullanılan dağıtık (distributed) versiyon kontrol sistemidir. 2005 yılında Linux'un yaratıcısı Linus Torvalds tarafından geliştirilmiştir.

Git hakkında bilmen gereken en temel 3 gerçek:

  • Bilgisayarında Çalışır: Git tamamen yerel (local) bir araçtır. Kullanmak için internete veya herhangi bir web sitesine ihtiyacın yoktur.
  • Hızlıdır: Sadece değişen kısımları akıllıca takip ettiği için binlerce dosyadan oluşan projelerde bile saniyeler içinde çalışır.
  • Git ve GitHub Aynı Şey Değildir: Yeni başlayanların en sık karıştırdığı nokta budur.
Git ve GitHub Farkı

Git, bilgisayarında çalışan ve versiyonları yöneten yazılımdır. GitHub ise Git ile yönettiğin projeleri internette yedeklediğin ve paylaştığın bir bulut platformudur. Önce Git'in mantığını oturtmak, tüm platformları (GitHub, GitLab, Bitbucket) kolayca kullanmanı sağlar.

Özetle

Git, projende her önemli adımda bir "kayıt noktası" (oyunlardaki save mantığı gibi) almanı ve istediğin zaman bu kayıt noktaları arasında güvenle dolaşmanı sağlayan araçtır.

2. Ders: Kurulum ve Temel Yapılandırma (git config)

Kurulum ve Temel Yapılandırma (git config)

Git'i kullanmaya başlamadan önce bilgisayarına kurman ve ona kim olduğunu tanıtman gerekir. Çünkü Git, ileride alacağın her kayıt noktasının (commit) üzerine "Bu değişikliği kim yaptı?" bilgisini bir imza gibi ekler. Bu ayarları bir kez yaparsın ve bilgisayarındaki tüm projelerde geçerli olur.

1. Git Kurulumu

  • Windows: git-scm.com adresinden Windows sürümünü indir. Kurulum sırasında karşına birçok teknik ayar çıkacaktır; şimdilik hiçbirini değiştirmeden Next diyerek varsayılan ayarlarla kurulumu tamamla. Kurulum bitince bilgisayarında Git Bash adında bir terminal uygulaması oluşacaktır.
  • macOS: Terminali açıp git --version yaz. Eğer kurulu değilse macOS sana kurulum penceresini otomatik olarak çıkaracaktır.
  • Linux (Ubuntu/Debian): Terminale sudo apt install git yazman yeterlidir.

2. Kurulumu Doğrulama

Terminalini (Windows'ta Git Bash, VS Code Terminali veya PowerShell) aç ve şu komutu yaz:

git --version # Örnek Çıktı: git version 2.4x.x

Ekranda git version 2.4x.x benzeri bir sürüm numarası görüyorsan Git başarıyla kurulmuş demektir.

3. Kendini Git'e Tanıtma (git config)

Şimdi Git'e adını ve e-posta adresini söyleyelim. Komuttaki --global ifadesi, bu ayarın sadece tek bir klasör için değil, bilgisayarındaki tüm Git projeleri için geçerli olmasını sağlar.

git config --global user.name "Adın Soyadın" git config --global user.email "eposta@adresin.com" # Örnek: git config --global user.name "Ahmet Yılmaz" git config --global user.email "ahmet.yilmaz@gmail.com"
İpucu

İleride GitHub kullanacaksan, buraya GitHub hesabında kullanacağın e-posta adresini yazman işini çok kolaylaştırır.

4. Varsayılan Ana Dalı main Yapma

Git eskiden projelerin ana dalına (branch) varsayılan olarak master adını verirdi. Modern standartlarda ise bu isim main olarak kullanılır. Her yeni projede isim değiştirmekle uğraşmamak için bunu tek seferde ayarlayalım:

git config --global init.defaultBranch main

5. Ayarları Kontrol Etme

Yaptığın tüm ayarların doğru kaydedildiğinden emin olmak için şu komutu çalıştır:

git config --list # Örnek Çıktı: # user.name=Ahmet Yılmaz # user.email=ahmet.yilmaz@gmail.com # init.defaultbranch=main

Çıktının içinde şuna benzer satırlar görüyorsan kurulum ve yapılandırma tamamdır. Artık Git seni tanıyor ve ilk projeni takip etmeye hazır. Bir sonraki derste bir klasörü Git deposuna çevirecek ve Git'in arka planda nasıl çalıştığını göreceğiz.

3. Ders: Depo Oluşturma ve Git'in 3 Alanı (init, status)

Depo Oluşturma ve Git'in 3 Alanı (init, status)

Git, bilgisayarındaki her klasörü otomatik olarak takip etmez; aksi halde tüm bilgisayarın gereksiz yere izlenirdi. Bir projeyi Git ile yönetmek istediğinde, önce o klasörü bir Git Deposuna (Repository) dönüştürmen gerekir.

1. İlk Deponu Oluşturma (git init)

Önce terminalde boş bir proje klasörü oluşturalım ve içine girelim (mevcut bir projen varsa doğrudan o klasörün içine cd ile girebilirsin):

mkdir satis-analizi cd satis-analizi

Şimdi bu klasörü Git'in takip edeceği bir depoya çevirmek için şu komutu yaz:

git init # Çıktı: # Initialized empty Git repository in .../satis-analizi/.git/

Arka Planda Ne Oldu? git init komutu, klasörünün içinde .git adında gizli bir klasör oluşturdu. Projendeki tüm versiyon geçmişi, ayarlar ve kayıt noktaları bu gizli klasörün içinde saklanır. (Gizli dosyaları göstermeyen dosya gezginlerinde görünmeyebilir; Git Bash'te ls -a komutuyla var olduğunu görebilirsin.)

Önemli: .git Klasörüne Dokunma

Bu .git klasörünü asla manuel olarak silme veya içindeki dosyaları elle değiştirme. Onu silersen kendi çalışma dosyaların kalır ancak projenin tüm versiyon geçmişi yok olur ve klasör tekrar sıradan bir klasöre döner.

2. Git'in 3 Temel Alanı (Zihinsel Model)

Komutları ezberlemek yerine Git'in çalışma mantığını anlamak işini çok kolaylaştırır. Git, dosyalarını 3 farklı aşamada (alanda) yönetir. Bunu bir fotoğraf çekimi gibi düşünebilirsin:

1. Çalışma Dizini (Working Directory)

Senin normal proje klasöründür. Kodlarını yazdığın, dosyaları düzenlediğin, sildiğin yer burasıdır.
(Fotoğraf çekilecek odadaki herkes)

2. Sahne Alanı (Staging Area)

Bir sonraki kayıt noktasına dahil etmek istediğin değişiklikleri geçici olarak topladığın bekleme alanıdır.
(Sadece fotoğrafa girmek için sahneye çağırdığın kişiler)

3. Depo (Repository)

Sahneye aldığın dosyaların kalıcı olarak kaydedildiği, zaman makinesinin arşividir (.git klasörü).
(Çekilen fotoğrafın albüme yapıştırılması)

Neden doğrudan kaydetmek yerine arada "Sahne" alanı var? Çünkü aynı anda birden fazla dosyada çalışıyor olabilirsin; sahne alanı sayesinde her şeyi tek seferde kaydetmek zorunda kalmadan, yalnızca o kayda dahil etmek istediğin değişiklikleri özenle seçebilirsin.

3. Git'in Pusulası: Durum Kontrolü (git status)

Git kullanırken nerede olduğunu, hangi dosyaların değiştiğini veya bir sonraki adımda ne yapman gerektiğini unuttuğunda yazacağın ilk komut her zaman git status olmalıdır.

Hemen test edelim. Klasörünün içinde analiz.py adında boş bir dosya oluştur ve durumu kontrol et (Git Bash'te touch doğrudan çalışır; editörden yeni dosya açman da aynı işi görür):

touch analiz.py git status # Çıktı: # On branch main # # No commits yet # # Untracked files: # (use "git add <file>..." to include in what will be committed) # analiz.py # # nothing added to commit but untracked files present (use "git add" to track)

Bu çıktıyı satır satır okuyalım:

  • On branch main: Şu an main (ana) dalında çalışıyorsun.
  • No commits yet: Henüz hiç kayıt noktası (versiyon) alınmamış.
  • Untracked files (Takip edilmeyen dosyalar): Git, analiz.py dosyasını gördü ama "Bu yeni bir dosya, bunu henüz sahneye almadın ve takip etmemi söylemedin" diyor (terminalde genellikle kırmızı görünür).
Güvenli Komut: Çekinmeden Sor!

git status yalnızca okuma yapar; hiçbir dosyanı değiştirmez veya silmez. Kafan karıştığı her an bu komutu çalıştırarak deponun o anki durumunu ve Git'in sana verdiği ipucu mesajlarını görebilirsin.

Artık depon hazır ve Git klasöründeki hareketleri görebiliyor. Bir sonraki derste bu dosyayı sahneye almayı (git add) öğreneceğiz.

4. Ders: Dosyaları Sahneye Alma (git add)

Dosyaları Sahneye Alma (git add)

Bir önceki derste analiz.py dosyasını oluşturduğumuzda git status bize bu dosyanın takip edilmediğini (untracked) söylemişti. Şimdi bu dosyayı kalıcı olarak kaydetmeden (commit) önceki durak olan Sahne (Staging Area) alanına alacağız.

Neden Doğrudan Kaydetmiyoruz?

Yeni başlayanlar genelde şu soruyu sorar: "Neden tek seferde kaydetmek yerine önce sahneye alıyoruz?" Bunu bir senaryoyla düşünelim: Projende aynı anda iki dosya üzerinde çalışıyorsun:

  • veri_temizleme.py dosyasını tamamen bitirdin, kusursuz çalışıyor.
  • grafik.py dosyası ise henüz yarım, içinde yarım kalmış denemeler var.

Sahne alanı sayesinde sadece biten veri_temizleme.py dosyasını seçip bir sonraki kayda hazırlayabilir, yarım kalan grafik.py dosyasını ise dışarıda bırakabilirsin. Yani git add, bir sonraki kayıt noktasına nelerin gireceğini seçme aracıdır.

1. Tek Bir Dosyayı Sahneye Alma

Geçen derste oluşturduğumuz analiz.py dosyasını sahneye almak için şu komutu yaz:

git add analiz.py

Bu komut çalıştığında terminalde herhangi bir başarı mesajı görünmez; Git'te sessizlik her şeyin yolunda olduğu anlamına gelir. Durumu görmek için hemen pusulamızı çalıştıralım:

git status # Çıktı: # On branch main # # No commits yet # # Changes to be committed: # (use "git rm --cached <file>..." to unstage) # new file: analiz.py

Changes to be committed (Kaydedilmeye hazır değişiklikler): analiz.py artık kırmızı değil yeşil görünür. Bu, dosyanın sahnede yerini aldığı ve bir sonraki kayda (commit) hazır olduğu anlamına gelir.

2. Birden Fazla veya Tüm Dosyaları Sahneye Alma

Projede birden fazla dosya değiştiğinde her birini tek tek yazmak zorunda değilsin:

  • Seçtiğin birkaç dosyayı eklemek için: Dosya adlarını aralarına boşluk koyarak yazabilirsin.
git add analiz.py rapor.txt
  • Klasördeki tüm değişiklikleri tek seferde eklemek için: Nokta (.) "bulunduğum klasördeki her şey" anlamına gelir.
git add .
İpucu: Noktadan (.) Önce Durumu Gör

git add . çok pratiktir ama kullanmadan önce mutlaka git status ile klasörde neler olduğuna göz at. Böylece yanlışlıkla yarım kalmış veya gereksiz dosyaları sahneye almaktan kurtulursun.

3. Sık Düşülen Tuzak: "Sahneye Aldıktan Sonra Değişiklik Yapmak"

Anlık Kopya (Snapshot) Kuralı

git add komutu, bir dosyayı "sonsuza kadar takip et" demek değildir; yalnızca o dosyanın tam o andaki halinin bir kopyasını sahneye koyar.

Örneğin şu sırayı izlediğini düşünelim:

  1. git add analiz.py yazdın (dosyanın 1. hali sahnede).
  2. Sonra vazgeçip analiz.py içine 5 satır daha kod ekledin.
  3. Bu durumda git status yazarsan analiz.py dosyasını hem yeşil (eski hali sahnede) hem kırmızı (yeni eklediğin 5 satır sahnede değil) olarak görürsün:
git status # Çıktı (Aynı dosya iki bölümde birden görünür!): # Changes to be committed: # new file: analiz.py (Yeşil - 1. hali sahnede) # # Changes not staged for commit: # modified: analiz.py (Kırmızı - Yeni eklenen 5 satır sahnede değil)

Yeni eklediğin satırların da kayda girmesi için tekrar git add analiz.py çalıştırman gerekir.

Dosyamız artık sahnede ve fotoğraf çekilmeye hazır. Bir sonraki derste bu sahnedeki değişiklikleri kalıcı bir versiyona dönüştürmeyi (git commit) öğreneceğiz.

5. Ders: Versiyon Kaydetme ve İyi Commit Yazma (git commit)

Versiyon Kaydetme ve İyi Commit Yazma (git commit)

Bir önceki derste analiz.py dosyasını sahneye (Staging Area) almıştık. Şimdi fotoğrafın deklanşörüne basma zamanı: sahnede bekleyen bu değişiklikleri kalıcı bir kayıt noktası olarak depoya (Repository) kaydedeceğiz. Git dünyasında bu işleme commit denir.

1. İlk Commit'ini Atma (git commit -m)

Değişiklikleri kaydederken Git senden mutlaka ne yaptığını açıklayan kısa bir mesaj ister. Bu mesajı terminalden doğrudan yazmak için -m (message) parametresini kullanırız:

git commit -m "analiz.py dosyası oluşturuldu" # Çıktı: # [main (root-commit) a1b2c3d] analiz.py dosyası oluşturuldu # 1 file changed, 0 insertions(+), 0 deletions(-) # create mode 100644 analiz.py

Bu çıktının sana söyledikleri şunlardır:

  • main: Kayıt, main dalına yapıldı.
  • a1b2c3d: Bu commit'in benzersiz kimlik numarasıdır (hash). İleride bu ana geri dönmek istediğinde bu kodu kullanacaksın.
  • 1 file changed...: Kaç dosyanın değiştiğini, kaç satır eklendiğini (insertions) ve kaç satır silindiğini (deletions) özetler.
Dikkat: -m Parametresini Unutma!

Eğer -m "mesaj" kısmını yazmadan sadece git commit yazarsan, Git senden mesaj istemek için terminal içinde bir metin editörü (genellikle Vim) açar. Yeni başlayanların en sık kilitlendiği yer burasıdır. Yanlışlıkla Vim'e düşersen klavyeden sırasıyla Esc tuşuna basıp :q! yazarak Enter'a basabilir ve çıkış yapabilirsin.

2. Kayıttan Sonra Durumu Kontrol Etme

Commit attıktan sonra hemen pusulamıza bakalım:

git status # Çıktı: # On branch main # nothing to commit, working tree clean

working tree clean mesajı, çalışma klasöründeki tüm değişikliklerin güvenle kaydedildiğini ve bekleyen hiçbir iş olmadığını gösterir. Artık dosyan Git'in zaman makinesinde kalıcı olarak koruma altında.

3. İyi Bir Commit Nasıl Olmalı?

git commit komutunu çalıştırmak kolaydır, ancak profesyonel bir geliştirici veya veri analisti olmanın farkı commit alışkanlığında ortaya çıkar.

A. Anlamlı Commit Mesajları Yaz

Aylar sonra geçmişe baktığında hangi kayıtta ne yaptığını tek bakışta anlayabilmelisin:

Kötü Mesajlar İyi Mesajlar
"güncelleme" "Eksik maaş verileri ortalama ile dolduruldu"
"hata düzeltildi" "Tarih sütunundaki format hatası giderildi"
"son hal v2" "Aylık satış grafiği için eksen başlıkları eklendi"
"asdfgh" "Regresyon modeli için eğitim/test ayrımı yapıldı"

B. Atomik Commit (Tek Kayıt, Tek İş) Mantığı

Tek bir commit'in içine birbiriyle alakasız 10 farklı değişikliği doldurma. Örneğin:

  • Veri temizleme işlemini bitirdin → 1. Commit
  • Grafik kodlarını ekledin → 2. Commit
  • Rapor metnindeki yazım hatasını düzelttin → 3. Commit

Her commit tek bir mantıksal işi temsil ederse, ileride sadece grafik kodunda bir hata çıktığında veri temizleme kodlarına hiç dokunmadan yalnızca 2. commit'i geri alabilirsin.

Temel Git Döngüsü Tamamlandı

Artık temel Git döngüsünü (değişiklik yap → git add → git commit) tamamladın. Bir sonraki derste, projede oluşan geçici dosyaları, şifreleri veya devasa veri setlerini Git'in takibinden nasıl gizleyeceğimizi (.gitignore) öğreneceğiz.

6. Ders: İstenmeyen Dosyaları Gizleme (.gitignore)

İstenmeyen Dosyaları Gizleme (.gitignore)

Bir proje klasöründe sadece senin yazdığın kodlar bulunmaz. Çalıştıkça klasörde geçici sistem dosyaları, büyük ham veri setleri veya içinde şifre/API anahtarı barındıran ayar dosyaları birikir. Bu dosyaların Git tarafından takip edilmesini istemezsin.

İşte tam bu noktada .gitignore devreye girer. Bu dosya, Git'e "Şu dosya ve klasörleri görmezden gel, git status veya git add . yaparken bunları bana hiç gösterme" demenin yoludur.

Neleri Gizlemelisin?

  • Hassas Bilgiler: Veritabanı şifreleri, API anahtarları (.env dosyaları). Bunları asla versiyon kontrolüne dahil etme.
  • Büyük Veri Dosyaları: Yüzlerce megabaytlık .csv, .xlsx veya .parquet ham veri setleri (Git kod takibi içindir, büyük veriler depoyu yavaşlatır ve şişirir).
  • Otomatik Oluşan Geçici Dosyalar: Python'ın oluşturduğu __pycache__/, R'ın oluşturduğu .Rhistory ve .RData, işletim sistemlerinin oluşturduğu .DS_Store (macOS) veya Thumbs.db (Windows) dosyaları.

1. .gitignore Dosyası Nasıl Oluşturulur?

Projenin ana klasöründe (.git klasörünün olduğu dizinde) tam olarak .gitignore adında bir dosya oluşturman yeterlidir. Başındaki noktaya dikkat et; uzantısı yoktur.

touch .gitignore

(Alternatif olarak VS Code veya kullandığın editörden doğrudan .gitignore adıyla yeni bir dosya da açabilirsin. Windows Dosya Gezgini başında nokta olan dosyalarda bazen isim uyarısı verebildiği için terminal veya editör kullanmak en pratik yoldur.)

2. Kurallar Nasıl Yazılır?

.gitignore dosyasının içine her satıra bir kural yazılır. Temel kurallar oldukça basittir:

  • Tek bir dosyayı gizlemek için: Tam adını yaz (gizli_ayarlar.txt).
  • Belirli bir uzantıdaki tüm dosyaları gizlemek için: Yıldız (*) kullan (*.csv, *.log).
  • Tüm bir klasörü gizlemek için: Klasör adının sonuna / koy (ham_veriler/, venv/).
  • Yorum satırı eklemek için: Başına # koy.

Bir veri analizi veya yazılım projesi için örnek bir .gitignore içeriği:

# Hassas ayar ve şifre dosyaları .env # Büyük veri dosyaları *.csv *.xlsx ham_veriler/ # Python geçici dosyaları ve sanal ortam __pycache__/ venv/ .ipynb_checkpoints/ # R geçici dosyaları .Rhistory .RData # İşletim sistemi dosyaları .DS_Store Thumbs.db

3. Çalıştığını Test Edelim

Klasöründe veriler.csv adında bir dosya olduğunu ve .gitignore içine *.csv yazdığını varsayalım. Şimdi pusulamızı çalıştıralım:

git status # Çıktı: # On branch main # Untracked files: # (use "git add <file>..." to include in what will be committed) # .gitignore # # (Dikkat: veriler.csv dosyası listede hiç görünmüyor!)

Çıktıda veriler.csv dosyasının hiç görünmediğini, sadece .gitignore dosyasının kendisinin Untracked files altında listelendiğini göreceksin.

Önemli: .gitignore Dosyasını da Commit'le

.gitignore dosyasının kendisini mutlaka git add .gitignore ve git commit -m ".gitignore dosyası eklendi" diyerek kaydetmelisin. Böylece gizleme kuralların da projenin bir parçası olarak saklanır.

4. Sık Düşülen Tuzak: "Dosyayı .gitignore'a Yazdım Ama Hâlâ Görünüyor!"

Önceden Takip Edilen Dosyalar Kuralı

.gitignore, yalnızca henüz takip edilmeyen (untracked) dosyaları görmezden gelir. Eğer bir dosyayı daha önce git add ve git commit ile depoya kaydettiysen, sonradan adını .gitignore'a yazsan bile Git o dosyayı takip etmeye devam eder.

Bu durumda dosyayı bilgisayarından silmeden sadece Git'in takibinden çıkarmak için şu komutu kullanırsın:

git rm --cached veriler.csv git commit -m "veriler.csv takipten çıkarıldı"

Bu işlemin ardından veriler.csv dosyası bilgisayarında durmaya devam eder ama Git artık onu tamamen görmezden gelir.
